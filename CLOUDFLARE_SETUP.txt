O-RA STORE - CLOUDFLARE FRESH SETUP
===================================

LOCAL TEST FIRST
1. npm install
2. npm run dev
3. Test http://localhost:3000
4. Test http://localhost:3000/system

CLOUDFLARE-RUNTIME LOCAL TEST (use local test data, never the live bucket)
5. npm run cf:dev

LIVE DEPLOY (only after local tests pass)
- GitHub: push this clean project
- Cloudflare: connect GitHub to a Workers project
- Build command: npm run build
- Deploy command: npx wrangler@latest deploy

Required live values
Build-time browser vars:
- VITE_SUPABASE_URL
- VITE_SUPABASE_PUBLISHABLE_KEY

Worker secrets:
- SUPABASE_SECRET_KEY
- ORA_SUPER_ADMIN_PASSWORD
- ORA_DEFAULT_STAFF_PASSWORD
- STAFF_SESSION_SECRET
- ABUSE_HASH_SALT

Optional later:
- GEMINI_API_KEY
- GROQ_API_KEY
- FARDAR_* values

IMPORTANT
- Do not place secret values in GitHub files or wrangler.jsonc.
- /system SPA fallback is configured in wrangler.jsonc.
- /api/* is routed to the Worker backend.
- Live operational data is stored in the existing ORA_MEDIA_R2 bucket:
  orders, catalog/stock/settings, staff accounts, waybill locks, courier cities,
  reports, reviews, requests, analytics and notifications.
- Supabase remains for customer Google sign-in and email OTP. Its Data API is
  not used for normal live operational reads/writes after the R2 recovery.
- Keep the existing Supabase URL and server key: the SDK query adapter uses
  them to identify server-side data requests without sending those requests
  to Supabase. Customer auth requests still use Supabase.
- Private R2 records and backups use AES-GCM; /api/media serves media/ only.
- Preserve STAFF_SESSION_SECRET (or ABUSE_HASH_SALT if that is the configured
  key). Changing that server secret requires decrypting and re-encrypting data
  with the old key first. Ordinary staff password changes do not change it.
- The active manifest is ora-data/active-v2.json. Table writes use conditional
  ETags to retry conflicts instead of losing concurrent writes.
- Before table changes, the previous table is saved in one of 168 hourly
  backup slots per table under ora-data/backups-v2/ (seven days, bounded).
  Slot metadata records the actual hour. Backups use their original object
  paths as authenticated encryption context; decrypt before restoring them.
- /tmp is never an acknowledged fallback for live durable data.
- The one-time encrypted migration asset and import credential are removed
  after successful recovery. /api/cloudflare-recovery/import returns 410.
- Authenticated /api/cloudflare-recovery/status reports the current R2 count.
- Regression check: node --import tsx tools/test-cloudflare-data.ts

LOSSLESS STORAGE COMPRESSION
- ORA_R2_COMPRESSION_ENABLED=1 writes compressible private JSON with native
  level-1 gzip before AES-GCM encryption (ora-aes-gcm-v2). Small objects stay v1.
  All readers accept both formats; v2 authenticates its encoding and object path.
- Deploy compatible readers before enabling the flag. To stop compression,
  disable the flag while retaining the compatible reader; older pre-codec
  releases cannot decode compressed objects and must not be used for rollback.
- Cron gradually re-encodes one current table/old backup per run. It verifies
  the exact decompressed string and uses ETag CAS so active staff edits win.
  Metadata and the 168 hourly slots stay intact; no business fields change.
- New identical product/branding uploads share a SHA-256 media key without
  changing any uploaded bytes. Existing media URLs keep working. Customer
  submissions/receipts keep separate random keys. This does not delete images.

DELIVERED CSV AND FACEBOOK AUDIT
- Authenticated order list/version reads use the Worker R2 path directly,
  avoiding repeated whole-table serialization through the SDK and Node bridge.
- Decrypted table caches are checked against a fresh R2 ETag on every read.
  Failed writes never alter cached records; unchanged updates avoid extra writes.
- Delivered CSV sends at most 20 delivery-only entries per atomic R2 write.
  It matches the current waybill/order, permits Shipped -> Delivered, preserves
  invoice/stock locks, updates delivery and tracking status, and skips repeats.
- Sheet catch-up runs from cron, not each normal website/API request.
- /fb-lead-audit compares today's Facebook leads, current R2 orders and
  physical Sheet rows. It requires an active Super Admin session, pages through
  form/lead results, and marks any failed/incomplete source as incomplete.
  Requests check two forms concurrently, with bounded pagination. The page shows
  checked forms and running/completed state, retries temporary HTTP failures,
  and only offers a final report after every form and matched Sheet order check.
